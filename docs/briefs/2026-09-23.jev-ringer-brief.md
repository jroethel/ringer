## Outcome

Ringer uses Jev for two decisions it makes badly today.
First, the `task_type` recorded for each task: in the pilot's blind review, hand labels lost 38 to 14 where they disagreed with Jev.
Second, whether a FAIL is the check's fault, decided before ringer spends its automatic retry on it.

Presupposition verdicts:

- The adoption brief's rule "the hand-assigned value, when present, always wins" would make the feature a no-op, because 214 of 214 logged attempts are already hand-typed.
  It is reversed: Jev's label is recorded when its confidence meets a configurable cutoff.
- Issue #65's non-goal of auto-detecting check bugs is revisited in proposal-only form.
  Jev never writes an amendment; it skips one automatic retry and proposes the exact `amend` command for a human to run.

## End artifact

- Fewer wasted retries in live runs: 16 of the 50 logged retries were on tasks later amended as check or spec faults, though 1 of those 16 retries passed.
- A per-task_type scoreboard trustworthy enough to route real work on.
- A reusable Jev integration pattern (switches, fallback, logging, a declared list of what leaves the host) to carry into RIT data work.

## Done looks like

With the Jev switches on:

- `./ringer.py lint manifest.json` shows, per task, the Jev label, its confidence, and whether it overrides the hand label.
- In `./ringer.py run manifest.json`, a FAIL that Jev flags as a suspected check fault skips the automatic retry, prints the suspected cause plus the exact `./ringer.py amend <run_id> <task_key> --reclassify check_bug --note "..."` command, and records all three on the FAIL's log row.
- `./ringer.py models` ranks on the recorded task_type and shows, per bucket, how many rows were labeled by hand and how many by Jev.
- The switch documentation lists exactly which fields each decision point sends to TypeSafe, and the size cap on each.

In every case:

- With the master switch off, the API key unset, or the API unreachable or hanging, ringer behaves exactly as it does today.
- `python3 -m unittest discover -s tests` passes offline with no key.

## Approach

Chosen (decided 2026-09-23): A, a stdlib HTTP client inside `ringer.py`, behind a master switch plus one switch per feature, all default off.
It calls `POST https://api.typesafe.ai/v1/systemone` directly with the key read from the environment.
Because ringer runs tasks concurrently on one asyncio event loop (`ringer.py:8945-8955`), every call runs off the event loop and carries a hard timeout, so a slow or hanging API can never stall other tasks.
Any failure (no key, network error, timeout, non-200, rate-limited) falls back to today's behavior.
At about 100 calls a month, ringer does not retry Jev calls itself; a failed call just means the fallback.

Alternatives considered:

- B: a sidecar package on `typesafe-sdk`, which brings built-in 429 backoff but breaks the single-file stdlib-only rule and needs a venv on every host.
- C: ringer calls a user-configured external command, the way it calls engines; most portable, but adds a process boundary and a second thing to install on every host.
- D (FAIL flag only): fixed code signatures such as sandbox or network blocked or a missing fixture, with no Jev.
  Declined as the whole answer, because the evidence in #65 is semantic: a grep matched the stub the spec asked for, and a check demanded a state the spec forbade.
  Fixed signatures remain a possible cheap first pass (Parking lot).

Rationale: A matches the house rule (`CONTRIBUTING.md:18`), and falling back is safe because today's behavior is the fallback.
The reusable part for RIT is the pattern, not the code.

Dated ecosystem facts this rests on, read from docs.typesafe.ai on 2026-09-23:

- One endpoint, `POST /v1/systemone`, with the `model` field selecting the model.
- `jev-1.13.0` is the only current model; `jev-latest` and `jev-preview` both point to it.
- The docs recommend pinning a versioned ID once thresholds are tuned, and logging the response's `model` field.
- Rate limits are 1,200 requests per minute and "can change without notice"; callers using the HTTP API directly handle `429` themselves.
- Price is $0.042 per million input tokens, output free.

## Success criteria

1. `[executed-check]` All Jev switches default to off in a fresh config.
   With them off, lint output for a sample manifest matches today's output exactly, and the test suite passes with `TYPESAFE_API_KEY` unset and no network.
2. `[executed-check]` If the switches are on but the key is missing, or the endpoint refuses, hangs past the timeout, or rate-limits, lint and run still finish with today's behavior.
   They print one line naming why Jev was skipped.
   A test with a hanging stub shows other concurrent tasks keep running while one Jev call waits.
3. `[executed-check]` With the stub serving the pilot's recorded responses, Jev's label is recorded when its confidence is at or above the cutoff and its class is not held out; otherwise the hand label is recorded.
   Each log row carries the hand value, Jev value, confidence, which one was used, `model`, and `usage`.
4. `[executed-check]` Both cutoffs (task_type and FAIL flag) and the held-out class list are config values.
   The cutoffs default to 0.9 and the held-out list to `research`, `probe`, and `persona-review`, which you release by editing the list.
   A test shows that changing the task_type cutoff changes which label is recorded.
5. `[executed-check]` Each decision point sends one batched Jev request, never one request per question.
6. `[executed-check]` With the stub, a FAIL that Jev flags on a `max_attempts=2` task runs exactly one attempt.
   The FAIL's log row records the flag, the suspected cause, and the proposed `amend` command, and the same three are printed.
   A FAIL Jev does not flag retries as it does today.
7. `[executed-check]` A flagged run writes no amendment rows; only the `amend` command writes them.
8. `[executed-check]` A test asserts that each decision point's request carries only the fields listed in the switch documentation and stays under its size cap.
   The live FAIL flag and the offline replay send the same field set, so the replay validates what the live flag sees.
9. `[executed-check]` The offline replay counts per task, on each task's first FAIL, since that is the FAIL that gates the retry.
   The 17 amended tasks are labeled check_bug or spec_defect from their amendment notes before the replay runs.
   The replay writes a results file showing that at least 9 check_bug tasks were flagged.
   A flag on a task whose logged retry passed counts as a false flag.
10. `[judgment]` Your hand review of flags on un-amended tasks, plus the false flags counted in criterion 9, totals at most 20% of all flags.
    A script cannot check the hand-review part, because un-amended FAILs have no verified label.
    The FAIL-flag switch stays off until criteria 9 and 10 both pass.
    One rewording of the questions and one more replay are allowed; if it still misses, the FAIL flag is parked and the task_type work ships alone.
11. `[executed-check]` Against a sample log mixing hand-labeled and Jev-labeled rows, `./ringer.py models` groups results by the recorded task_type and shows the hand and Jev count for every bucket.

## Seams

In blast-radius order, most downstream-breaking first:

1. Jev plumbing: config, switches, off-loop stdlib client with timeout, stub, call logging, and the declared field list per decision point.
   Both features depend on it, and its offline tests check it on its own.
2. task_type recording and scoreboard, including the `ringer.db` read-model schema and ingest, which store a single `task_type` today (`ringer.py:6713`).
   Depends on 1.
3. Offline FAIL replay.
   Changes nothing in ringer's runtime, depends only on 1's client and field list, and can run alongside 2.
   It is the gate for 4.
4. FAIL flag in the retry path.
   Depends on 1 and on 3 passing, and goes last because it touches the retry loop, the largest runtime blast radius.

## Known vs guessed

Verified this session (2026-09-23):

- `~/.ringer/runs.jsonl` holds 214 attempts, 74 FAILs, and 17 `check_bug` amendments, all written on 2026-08-21 and all tracing back to glm-5.2 FAILs.
- The 17 amended tasks have 33 attempts: 29 FAIL, 2 TIMEOUT, 1 ERROR, and 1 PASS.
- The PASS is `task3-uat-loader`, a retry that succeeded, and its amendment note starts "spec defect"; 3 of the 17 amendment notes mention the spec.
- 16 of 50 retries, taking 213 worker-minutes, were on amended tasks.
- 0 of 214 attempts are untyped; the held-out classes have 1 (`research`), 1 (`probe`), and 4 (`persona-review`) logged samples.
- 166 of 214 attempts (78%) ran on glm-5.2.
- The automatic retry is at `ringer.py:9035`, and `max_attempts` defaults to 2.
- Tasks run concurrently through `asyncio.gather` under a semaphore (`ringer.py:8945-8955`).
- The stdlib-only rule is at `CONTRIBUTING.md:18`; config is TOML loaded by `AppConfig`.
- The TypeSafe endpoint and model facts listed under Approach.

Verified by the Rubix reviewer, not re-checked here:

- `models` buckets by the recorded task_type (`ringer.py:5978`), and `CONTRIBUTING.md:11` requires displayed data to be true.
- Logged FAIL rows carry `spec` and the check output inside `notes`, but no check command and no worker log excerpt.

Believed but unchecked:

- That the check_bug-labeled amendments represent check bugs in general; they come from one session on one model.
  If not, the replay bar says little about new kinds of check bug.
- That Jev can catch the spec-versus-check contradictions from #65; the jev-1.13 jaggedness page lists indirection as a weakness.
  If not, the replay misses the bar and the FAIL flag is parked.
- That the pilot's calls ran on `jev-1.13.0`; they used the `jev-latest` alias, which points there today.

Guessed:

- That future retry waste resembles the past; one episode dominates, with 12 of the 33 amended-task attempts from two runs.
  If wrong, the FAIL flag saves little.
- That the scoreboard grows more sensitive to task_type as the model mix spreads beyond 78% glm-5.2.
  If wrong, better labels change few routing decisions.
- That `429` responses are rare at about 100 calls a month.
  If wrong, the fallback fires more often and Jev's coverage drops.
