## Why it misses

The check_bug labels came from gate audits that could see the check script and the worker's diff.
Jev sees neither: the declared fields are the first 500 characters of the spec and the check's printed output.
Example: `task-09-condense-tableau` was labeled check_bug because the check ran a repo-wide negative grep over historical docs the spec forbade the worker from touching.
Its check output reads `design section incomplete: studio/designs/cash-and-commitments/report-card.md`, which looks exactly like a worker fault, and Jev answered `worker` at 0.97 with cause `out_of_scope`.
The boundary that would have flipped that answer lives in the spec's BOUNDARY section past the 500-character cap and in the check script, neither of which was sent.
The pilot's task_type success does not transfer here: a spec's opening sentences carry its type, but a check bug is a property of the check, which the flag never reads.

## Candidates for the next brainstorm

1. Send the check script text as a declared field (new privacy declaration in `docs/JEV.md`, a cap, and a redaction decision), so Jev can read what is broken instead of inferring it from the output.
2. Send the spec's boundary or ownership section rather than its first 500 characters, or raise the cap; the boundary is where most check_bug evidence lives.
3. A fixed-signature pre-pass for the `syntax_or_transport` class (already parked as jroethel/ringer#3); Jev chose that cause on four of the pairs it did call `check`, which suggests those may not need a model at all.
4. Send the worker's changed-file list (live runs have the worktree; the log does not), which would let the `out_of_scope` cause be checked rather than guessed; a replay would then need a different ground truth.
5. Revisit the bar and the cutoff only after the fields change; the v1 numbers show the information, not the threshold, is the limit.
6. The brief's open question of Noul probabilities versus a Choice with an `uncertain` option is still open.
