## 4. Hazard mitigations

Each item names the hazard and the mitigation; DEVIATION marks a change from how the source plan says to run or check a task (never from what it produces).

1. Check custody.
   Every check lives inline in an orchestrator-owned manifest; no worker owns a check file.
   Because the workers author the test files, each check also compares every file and block the plan gives "exactly" or "verbatim" against the committed plan (read with `git show HEAD:`), so a worker cannot weaken its own tests and pass.
2. Deliverable loss on a passing worktree.
   Workers leave changes uncommitted; each check stages with `git add -A` and exports `git diff --cached --binary` to `/home/jjrdar/ringer-work/jev-ringer/patches/<key>.patch`, and `expect_files` names that absolute path.
   None of the owned paths is gitignored (verified with `git check-ignore` on 2026-09-23); the one outside-git output, Task 4's `labels.json`, is verified in place by its check.
3. Check cwd (MODEL-NOTES 2026-09-17 and 2026-09-19 SIGNAL lines).
   Checks run at the worktree root and never `cd` to the main checkout; each check fails loudly if its cwd is not a worktree root or is `/home/jjrdar/repos/ringer`.
   DEVIATION: every `cd /home/jjrdar/repos/ringer && ` prefix in the embedded plan text is removed from the specs, and the specs forbid touching the main checkout.
4. Ringer's 60-second check ceiling (`CHECK_TIMEOUT_S = 60`, ringer.py:55; MODEL-NOTES 2026-09-13).
   The baseline suite alone took 31 seconds on 2026-09-23, and the Jev test files add stub timeouts and CLI subprocesses, so "unit file plus full suite" cannot fit inside a check by wave 3.
   DEVIATION: each ringer check runs the unit's test file plus a named regression subset (idle estimate 20 to 45 seconds per check, not measured), and the full suite runs in the worker's self-check, in every validator, and at every gate on `jev-ringer`.
   A check that times out is a check-bug attribution (trim the subset, BATCH if 15 lines or fewer), never a worker fault.
5. Vacuous greens.
   Each check first asserts the unit's new test file exists, then requires `Ran N tests` with N greater than 0; `./ringer.py run --baseline` must report every check FAIL before each wave launches, which is this run's non-vacuity proof (the committed expected-fail fixture convention is not yet authored in the ringer skill, so there is no live mutate-and-restore probe).
6. Eval-log self-contamination.
   This run writes its own attempt rows to `~/.ringer/runs.jsonl`, so any FAIL in waves 1 or 2 would add a FAIL pair and break Task 4's exact dry-run line.
   DEVIATION: pre-flight freezes the log to `/home/jjrdar/ringer-work/jev-ringer/runs-snapshot.jsonl`; Task 4's worker and check dry-run the snapshot, and the check also counts the snapshot independently and reports a LOG-DRIFT finding (not a worker fault) if it does not hold 47 FAIL pairs, 15 amended, 20 retry-passed.
   The check prints the live-log dry run as information only.
7. Worker commits and wave bases.
   Ringer bases each worktree on the `jev-ringer` HEAD at launch, so wave N's patches are committed before wave N+1 launches.
   Each check fails if the worktree HEAD differs from the current `jev-ringer` tip, which catches a worker commit.
   Rule: nothing is committed to `jev-ringer` while a wave is running, and a stopped unit's check is re-run for attribution before any patch from its wave is applied.
8. Shared single file `ringer.py`.
   Tasks 1, 2, 3, and 5 edit it and run in separate waves; wave 2 pairs Task 2 with Task 4, which never edits `ringer.py`, so within-wave ownership is disjoint by construction and a conflict at apply time is a scope violation (STOP), never something to resolve quietly.
9. Live key and live calls.
   Every ringer and test command runs under `env -u TYPESAFE_API_KEY`; pre-flight confirms `~/.config/ringer/config.toml` has no `[jev]` table; no unit makes a live call, and the owner fires every live step.
10. Failed-task worktrees persist.
   A stopped unit keeps `/home/jjrdar/ringer-work/jev-ringer/<key>`, and ringer refuses to relaunch into an existing taskdir; after attribution, remove it with `git -C /home/jjrdar/repos/ringer worktree remove --force /home/jjrdar/ringer-work/jev-ringer/<key>` before any relaunch.
11. Self-update.
   Every orchestrator ringer command passes `--no-self-update` and exports `RINGER_NO_SELF_UPDATE=1`, so ringer never pulls or re-execs itself on the branch under construction.
12. Commit steps.
   DEVIATION: each plan task's final Commit step is removed from its spec (ringer lint blocks commit instructions under worktrees); the orchestrator commits each validated patch with the plan's exact message and no co-author trailer.
13. Resume pointers.
   DEVIATION: each unit's ownership list gains `docs/handoffs/2026-09-23.<key>.resume.md` (loop-drive Step 5); it travels in the unit's patch and lands in the unit's commit.
14. Read-model stamp flip after wave 3.
   Old code re-stamps any read-model schema other than 3 back to 3 (ringer.py:6696), and Task 3 moves it to 4; a Ringside process started from pre-Task-3 code and still running after the wave 3 commit would fight the new stamp on `~/.ringer/ringer.db`.
   Watch point: after the wave 3 commit, restart Ringside before wave 4 and read `sqlite3 ~/.ringer/ringer.db 'PRAGMA user_version'` at the wave 4 gate (expect 4).
15. Dirty working tree.
   The gate journal was committed first (8d0ab4a); any other uncommitted change at pre-flight or at any wave launch is a STOP that autonomy never resolves.

### Stopped units and slip rules

- Ringer's built-in retry is the repair pass; a unit that fails at its attempt limit is stopped.
- A worker fault is relaunched once, never resumed: add the itemized failure to that unit's spec (BATCH if 15 lines or fewer and it leaves the produced contract unchanged, else STOP), remove the kept worktree (hazard 10), and run a one-task relaunch manifest with the same `run_name`, for example `python3 -c 'import json,sys; m=json.load(open(sys.argv[1])); m["tasks"]=[t for t in m["tasks"] if t["key"]==sys.argv[2]]; m["max_parallel"]=1; json.dump(m, open(sys.argv[3],"w"), indent=2)' docs/plans/jev-ringer-loop/wave-$W.json $KEY $WORK/relaunch-$KEY.json`, then lint, baseline, and run it like a wave.
- A validator `fail` on a ringer-passing unit is handled the same way, with the validator's itemized findings as the spec addition.
- A validator `spec-problem` goes to the orchestrator: a spec edit of 15 lines or fewer confined to one unit that leaves its produced contract unchanged is BATCH; anything else is a STOP.
- A unit that fails validation twice is re-routed by the routing chain with the reason recorded: glm-5.3 to glm-5.2, then to opus; an opus unit has no stronger worker (Fable is never a worker), so a second opus failure is a STOP.
